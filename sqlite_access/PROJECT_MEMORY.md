# Project Memory

Last updated: 2026-10-31

## Product direction

- Build a progressively enhanced database application centered on SQLite compatibility.
- The product name is DataNook; SQLite remains the database engine and compatibility target.
- Progressively add useful facilities inspired by both Microsoft Access and LibreOffice Base; use them as product and workflow references without assuming full feature parity.
- The application runs entirely in a Chromium based browser, using HTML, CSS, and JavaScript on the client. There is no application server.
- Once a browser database has been established, persist it automatically.
- Update this file whenever project changes alter the product, architecture, or user-visible behavior.

## Current starting point

- A static SQL workspace with a query editor, run action, result tables, and a list of user tables.
- Horizontal Datasheet, Table Designer, Relationships, Query Design, SQL Editor, and Report Design tabs provide an Access and LibreOffice Base inspired navigation model. The query designer, SQL editor, relationship designer, and report section designer are only visible on their own tabs; table browsing and data operations live in Datasheet.
- Datasheet displays the selected table in an editable, spreadsheet-style grid. Users can search across displayed values, filter each field by distinct values using a searchable checkbox menu, sort by one field ascending or descending, and clear all view controls with one action. Search, filters, and sorting affect only the view and never change stored table order. Multiple field filters combine. A field with an active filter displays a funnel icon in its header filter button. Filter menus render in a fixed page-level overlay positioned against the viewport, flipping above the field and shifting away from screen edges as needed. For large distinct-value lists, the menu shows the first 500 matches and its search can find other values. Filtered and sorted rows remain editable, including multirow paste. Users can copy cell selections, paste tab-delimited spreadsheet ranges, and enter new records in a trailing blank row. Changes save to IndexedDB automatically. A mobile table selector supplements the desktop table list.
- Table Designer creates tables with selectable SQLite types, primary key, required, unique, default, and integer auto-increment field properties. Clicking a datasheet field heading opens the full table design with that field focused. During table editing, a Cancel button discards unsaved designer changes and returns to Datasheet. Saving rebuilds the table transactionally, migrates compatible records, and retains foreign keys, indexes, triggers, and AUTOINCREMENT sequence state. Tables with unsupported constraints (CHECK, COLLATE, generated columns, STRICT, WITHOUT ROWID, composite primary keys, or composite/partial unique indexes) are guarded from edits so their schema is not silently lost.
- In Datasheet, a red × beside the selected table deletes it after an in-app confirmation. The table and its records are removed, and the active workspace is refreshed and autosaved. Deletion is blocked while another table has a foreign key referencing it; those relationships must be removed first.
- Relationships lays out table and field cards with Access-style one-to-many connectors. Users drag title bars to reposition tables; the arrangement is stored in IndexedDB separately from SQLite and restored for the active browser database. Opening or creating another database resets the current arrangement. Users drag a primary-key or unique field onto a compatible field to create a foreign key; existing orphan values and duplicate relationships are checked before the change. New relationships use `ON UPDATE CASCADE` and `ON DELETE RESTRICT`; foreign-key checks are enabled in sql.js. A selected connector can be removed, rebuilding the child table while preserving its data and other supported schema objects.
- Query Design provides an Access-style table canvas and field grid. Users add tables from the table list, move the cards, then double-click or drag fields into the grid; the same source field can be added multiple times as independent grid rows. A calculated field can be added with a named SQLite expression, validated against the selected tables and emitted as a query-only column without changing the database schema. Calculated expressions participate in show, sort, criteria, grouping, and aggregate choices. Grid rows can be reordered by drag-and-drop or, when focused, with Alt+ArrowUp/Down; generated SELECT fields follow this order. Keyboard Enter/Space also adds a focused field. Existing foreign-key relationships are drawn between linked fields and compiled as `LEFT JOIN`s; disconnected tables use `CROSS JOIN`. The grid supports Show, sorting, and criteria. Its Totals mode adds per-row Group By, Sum, Avg, Count, Min, Max, and Where choices; group criteria compile to `WHERE`, aggregate criteria to `HAVING`, and grouped fields compile to `GROUP BY`. Repeated output columns get distinct aliases, using labels such as `Sum of credits` for a repeated aggregate. Users can run generated SQL or open it in SQL Editor. Query layout and grid settings remain in memory for the current design session; the named saved-query catalog stores the generated SQL definition.
- Report Design is the only report workflow and uses an Access-inspired section canvas. Bound fields can be added to any available section through the destination selector or moved, reordered, and removed; static text labels can be placed in report, page, group, and detail sections. Group/sort levels are ordered (maximum ten), movable, and support exact values, year/quarter/month/week/day, first one to five text characters, and numeric ranges. Group levels can show headers/footers in the canvas and independently include either band in preview/export. Group Header has a **Hide group value** checkbox; when checked, it suppresses only the generated group heading, retaining explicitly placed bound controls, static labels, and the band. Bound controls in group headers and footers display values only, like Detail rows; field names remain visible on their design-canvas controls. Group levels also apply record count and one selected Sum/Avg/Min/Max/Count Values summary, show percent of grand total, and choose print behavior. Detail rows can be hidden; a grand total is optional. Page headers and footers map to repeating print sections; bound fields there currently use the first and last result rows, respectively. Group-heading repetition after a page split and multiple summaries per level are future work. Separate design JSON records are saved, loaded, replaced, and deleted in `__APP_SAVED_REPORT_DESIGNS_DO_NOT_EDIT`; query-based designs restore after their saved SQL is run. Word `.docx` and Excel `.xlsx` downloads are generated from the current Report Design preview. `REPORT_DESIGN_FEATURES.md` tracks the Access research, scope, and Edge verification status.
- The SQL Editor can save, load, replace, and delete named query definitions in `__APP_SAVED_QUERIES_DO_NOT_EDIT`. Report Design definitions are stored in `__APP_SAVED_REPORT_DESIGNS_DO_NOT_EDIT`. The retired Reports-tab catalog `__APP_SAVED_REPORTS_DO_NOT_EDIT` is preserved and protected in older databases, but new databases no longer create it and the app no longer exposes its saved-report workflow. These app-managed tables travel with the database, are excluded from normal table browsing, and direct SQL modification is blocked in the editor. Other legacy `__app_*` internal tables are removed on open; these catalogs are intentional exceptions.
- Saved-query naming, replacement confirmation, and deletion confirmation use in-app HTML dialogs, avoiding unsupported browser `prompt()`/`confirm()` calls. Save/delete failures are shown in the editor status area.
- Main workspace content uses 95% of the viewport width, and tablet layouts stack the query designer/report controls at widths up to 900px for iPad portrait use.
- CSV/TSV import is available from Table Designer via **Import CSV as table**. It creates a new table after preview, delimiter selection/detection, and header choice; the first row is used as field names by default, and the remaining rows are imported as records. Quoted fields and multiline values are parsed; duplicate/empty headers are made unique. Imported values use SQLite `TEXT`. Existing table names are never replaced.
- SQLite executes through the pinned `sql.js` WebAssembly build (`1.14.2`). Excel and Word export use pinned JSZip (`3.10.1`) to package OOXML files in the browser. The library assets load from cdnjs; the app needs internet access to load those assets.
- The SQLite database is exported to IndexedDB on startup and after query execution, grid edits, CSV import, table creation, saved-query changes, and report-design changes. It is local to the browser profile and origin. It contains user tables plus the app-managed saved-query and report-design catalogs (and possibly a preserved legacy saved-report table); editor drafts and the displayed database filename are stored as separate IndexedDB values.
- Users can open `.sqlite`, `.sqlite3`, and `.db` files and use Save as to create a portable database copy. Chromium's File System Access API is used when available: after read/write permission is granted, normal autosaves update both the selected file and the IndexedDB copy. Other browser contexts use a file upload and download fallback, while continuing to autosave to IndexedDB.
- New database creates a blank SQLite database after a replacement confirmation and prompts for its initial file location in Chromium. In fallback contexts it downloads an initial file. It also becomes the active IndexedDB database and auto-saves there.
- The current SQL Editor draft is stored separately in IndexedDB and auto-saved after a short typing pause, on blur, and before running a query. The latest draft is restored on startup. Saved query and report definitions live in hidden SQLite tables; transient workspace state remains in IndexedDB.
- SQL Editor autocomplete suggests SQLite keywords, functions, table names, and field names from the active database. Table names are prioritized after `FROM`, `JOIN`, `INTO`, `UPDATE`, and `TABLE`; typing filters suggestions, arrows navigate, Enter/Tab completes, and Ctrl/⌘+Space opens suggestions at the cursor.
- The SQL Editor shows a compact Venn diagram beside the query box for every detected `INNER`, `LEFT`, `RIGHT`, `FULL OUTER`, and `CROSS` join. Each diagram labels its input tables when recognizable and explains which rows are retained. Queries without joins show a no-join hint; numerous diagrams scroll within the panel. On narrow phone viewports the diagrams stack below the editor; they remain alongside at iPad portrait widths.
- First launch loads the `school-demo.sqlite` file in the project folder: 30 students, 10 teachers, eight subjects, and 93 enrollments. The `students`, `teachers`, `subjects`, and `enrollments` tables use `_id` primary keys; there are no separate student numbers, teacher codes, or subject codes. No foreign-key constraints, year-level table, saved queries, or saved reports are preloaded. The matching SQL dump embedded in `app.js` is used if a browser opened from `file://` cannot fetch the SQLite asset. The active database is then saved in IndexedDB and restored on later launches.
- Source files are `index.html`, `styles.css`, and `app.js`; `README.md` describes how to launch the app.
- `TODO.md` holds the short, researched project roadmap. Keep priorities focused on local database safety and everyday Access/Base workflows; defer server, sync, scripting, and open-ended design features.
- `SMOKE_CHECKS.md` contains the lightweight manual regression checklist. The New database confirmation uses the in-app dialog so Chromium preserves the user gesture required to open its initial save picker.
- The app header groups Paul Gavini’s YouTube, resources homepage, and Help links beside the DataNook brand. The Help page explains the main workflows, links directly to download `school-demo.sqlite` for practice, and includes an “as is” disclaimer covering warranty, liability, and data backups.

## Constraints and current gaps

- No server side persistence, accounts, cross-device synchronization, or formal schema migration system are implemented yet.
- Site data removal or changing browser profile/origin removes access to the locally saved database.
- File auto-save depends on Chromium's File System Access API and the user granting read/write permission; in fallback contexts, Save as downloads a snapshot and later edits only auto-save to IndexedDB.
- Runtime requires the pinned JavaScript and WebAssembly assets from cdnjs. A later offline distribution can vendor these assets.
- IndexedDB stores a serialized SQLite database image after each query. This is suitable as a starting point; large database workloads and multi-tab coordination need deliberate design as features grow.
