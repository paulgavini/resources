# Project Memory

Last updated: 2026-10-22

## Product direction

- Build a progressively enhanced database application centered on SQLite compatibility.
- The product name is DataNook; SQLite remains the database engine and compatibility target.
- Progressively add useful facilities inspired by both Microsoft Access and LibreOffice Base; use them as product and workflow references without assuming full feature parity.
- The application runs entirely in a Chromium based browser, using HTML, CSS, and JavaScript on the client. There is no application server.
- Once a browser database has been established, persist it automatically.
- Update this file whenever project changes alter the product, architecture, or user-visible behavior.

## Current starting point

- A static SQL workspace with a query editor, run action, result tables, and a list of user tables.
- Horizontal Datasheet, Table Designer, Relationships, Query Design, SQL Editor, and Reports tabs, in that order, provide an Access and LibreOffice Base inspired navigation model. The query designer, SQL editor, relationship designer, and report creator are only visible on their own tabs; table browsing and data operations live in Datasheet.
- Datasheet displays the selected table in an editable, spreadsheet-style grid. Users can search across displayed values, sort by one field ascending or descending, and clear both with one action; search and sorting affect only the view and never change stored table order. Filtered and sorted rows remain editable, including multirow paste. Users can copy cell selections, paste tab-delimited spreadsheet ranges, and enter new records in a trailing blank row. Changes save to IndexedDB automatically. A mobile table selector supplements the desktop table list.
- Table Designer creates tables with selectable SQLite types, primary key, required, unique, default, and integer auto-increment field properties. Clicking a datasheet field heading opens the full table design with that field focused. Saving rebuilds the table transactionally, migrates compatible records, and retains foreign keys, indexes, triggers, and AUTOINCREMENT sequence state. Tables with unsupported constraints (CHECK, COLLATE, generated columns, STRICT, WITHOUT ROWID, composite primary keys, or composite/partial unique indexes) are guarded from edits so their schema is not silently lost.
- In Datasheet, a red × beside the selected table deletes it after an in-app confirmation. The table and its records are removed, and the active workspace is refreshed and autosaved. Deletion is blocked while another table has a foreign key referencing it; those relationships must be removed first.
- Relationships lays out table and field cards with Access-style one-to-many connectors. Users drag title bars to reposition tables; the arrangement is stored in IndexedDB separately from SQLite and restored for the active browser database. Opening or creating another database resets the current arrangement. Users drag a primary-key or unique field onto a compatible field to create a foreign key; existing orphan values and duplicate relationships are checked before the change. New relationships use `ON UPDATE CASCADE` and `ON DELETE RESTRICT`; foreign-key checks are enabled in sql.js. A selected connector can be removed, rebuilding the child table while preserving its data and other supported schema objects.
- Query Design provides an Access-style table canvas and field grid. Users add tables from the table list, move the cards, then double-click or drag fields into the grid; keyboard Enter/Space also adds a focused field. Existing foreign-key relationships are drawn between linked fields and compiled as `LEFT JOIN`s; disconnected tables use `CROSS JOIN`. The grid supports Show, sorting, and criteria. Its Totals mode adds per-field Group By, Sum, Avg, Count, Min, Max, and Where choices; group criteria compile to `WHERE`, aggregate criteria to `HAVING`, and grouped fields compile to `GROUP BY`. Users can run generated SQL or open it in SQL Editor. Query layout and grid settings remain in memory for the current design session; the named saved-query catalog stores the generated SQL definition.
- Reports show fields grouped under the starting table and all tables reachable through saved foreign-key relationships. Selecting a field from a related table automatically derives the shortest relationship path and generates the required SQLite `LEFT JOIN`s, retaining rows from the starting table. The displayed path identifies how each related table connects. Reports can alternatively use the latest SQL Editor result, sent to the report builder from the Results panel. Both source modes share field selection, sorting, grouping, preview, and Chromium print/PDF output. Group fields create nested sections in the order selected; each group shows a record count and can optionally show a `SUM` or `AVG` for one numeric field. New query results refresh query-based report fields and invalidate an old preview. Reports are generated on demand; reusable report definitions are not saved yet.
- The SQL Editor can save, load, replace, and delete named query definitions in the active SQLite database. Definitions live in `__APP_SAVED_QUERIES_DO_NOT_EDIT`, making them portable with the database file. The app-managed table is excluded from normal table, relationship, report, and autocomplete listings; common direct SQL writes to it are blocked in the editor. Its name warns users not to alter it in external tools. Other legacy `__app_*` internal tables are removed on open; this catalog is the intentional exception.
- Saved-query naming, replacement confirmation, and deletion confirmation use in-app HTML dialogs, avoiding unsupported browser `prompt()`/`confirm()` calls. Save/delete failures are shown in the editor status area.
- Main workspace content uses 95% of the viewport width, and tablet layouts stack the query designer/report controls at widths up to 900px for iPad portrait use.
- CSV/TSV import is available from Table Designer via **Import CSV as table**. It creates a new table after preview, delimiter selection/detection, and header choice; the first row is used as field names by default, and the remaining rows are imported as records. Quoted fields and multiline values are parsed; duplicate/empty headers are made unique. Imported values use SQLite `TEXT`. Existing table names are never replaced.
- SQLite executes through the pinned `sql.js` WebAssembly build (`1.14.2`). The library assets load from cdnjs; the app needs internet access to load those assets.
- The SQLite database is exported to IndexedDB on startup and after query execution, grid edits, CSV import, table creation, and saved-query changes. It is local to the browser profile and origin. It contains user tables plus the app-managed saved-query catalog; editor drafts and the displayed database filename are stored as separate IndexedDB values.
- Users can open `.sqlite`, `.sqlite3`, and `.db` files and use Save as to create a portable database copy. Chromium's File System Access API is used when available: after read/write permission is granted, normal autosaves update both the selected file and the IndexedDB copy. Other browser contexts use a file upload and download fallback, while continuing to autosave to IndexedDB.
- New database creates a blank SQLite database after a replacement confirmation and prompts for its initial file location in Chromium. In fallback contexts it downloads an initial file. It also becomes the active IndexedDB database and auto-saves there.
- The current SQL Editor draft is stored separately in IndexedDB and auto-saved after a short typing pause, on blur, and before running a query. The latest draft is restored on startup. Named saved queries are the only app-managed data stored in the SQLite file; transient workspace state remains in IndexedDB.
- SQL Editor autocomplete suggests SQLite keywords, functions, table names, and field names from the active database. Table names are prioritized after `FROM`, `JOIN`, `INTO`, `UPDATE`, and `TABLE`; typing filters suggestions, arrows navigate, Enter/Tab completes, and Ctrl/⌘+Space opens suggestions at the cursor.
- The SQL Editor shows a compact Venn diagram beside the query box for every detected `INNER`, `LEFT`, `RIGHT`, `FULL OUTER`, and `CROSS` join. Each diagram labels its input tables when recognizable and explains which rows are retained. Queries without joins show a no-join hint; numerous diagrams scroll within the panel. On narrow phone viewports the diagrams stack below the editor; they remain alongside at iPad portrait widths.
- First launch loads the `school-demo.sqlite` file in the project folder. It contains `students`, `courses`, and `enrollments`, with two foreign-key relationships from enrollments to the other tables. A matching in-code sample is used if a browser opened from `file://` blocks fetching the SQLite asset. The active database is then saved in IndexedDB and restored on later launches.
- Source files are `index.html`, `styles.css`, and `app.js`; `README.md` describes how to launch the app.
- `TODO.md` holds the short, researched project roadmap. Keep priorities focused on local database safety and everyday Access/Base workflows; defer server, sync, scripting, and open-ended design features.
- `SMOKE_CHECKS.md` contains the lightweight manual regression checklist. The New database confirmation uses the in-app dialog so Chromium preserves the user gesture required to open its initial save picker.
- The app header groups Paul Gavini’s YouTube, resources homepage, and Help links beside the DataNook brand. The Help page explains the main workflows, links directly to download `school-demo.sqlite` for practice, and includes an “as is” disclaimer covering warranty, liability, and data backups.

## Constraints and current gaps

- No server side persistence, accounts, cross-device synchronization, or formal schema migration system are implemented yet.
- Site data removal or changing browser profile/origin removes access to the locally saved database.
- File auto-save depends on Chromium's File System Access API and the user granting read/write permission; in fallback contexts, Save as downloads a snapshot and later edits only auto-save to IndexedDB.
- Runtime requires the pinned JavaScript and WebAssembly assets from cdnjs. A later offline distribution can vendor these assets.
- IndexedDB stores a serialized SQLite database image after each query. This is suitable as a starting point; large database workloads and multi-tab coordination need deliberate design as features grow.
